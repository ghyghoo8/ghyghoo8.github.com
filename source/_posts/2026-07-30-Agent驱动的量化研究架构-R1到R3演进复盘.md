## 摘要

本文以一个 A 股左侧量化研究平台为背景，介绍我在平台架构升级中承担的架构设计工作。随着研究版本持续增加，原有脚本式架构逐渐出现模块重复、流程耦合、数据权限失控、实验难以复现、运行中断后难以恢复等问题。针对这些问题，我采用分层架构与管道—过滤器思想，设计了“Agent 决策控制面、类型化研究工作流、Research Kernel、量化模块库、DataBroker 数据访问层、Evidence Journal 证据层”六层体系。系统通过不可变运行清单、信息分级、静态模块目录、内容寻址存储、追加式事件日志和首停机制，保证 Agent 可以驱动流程，但不能修改冻结协议或越权访问数据。项目分 R1、R2、R3 三阶段实施，先解决运行可追溯与故障恢复，再验证模块跨工作流复用，最后完成模块目录和类型化编排。实践表明，该架构显著提高了研究流程的可维护性、可扩展性、可恢复性和证据可信度，也为后续快速构建新的量化研究工作流奠定了基础。

## 一、项目背景

我参与建设的是一套面向 A 股左侧主动发现的量化研究平台。平台需要从历史行情、财务、题材、公告及市场结构数据中，识别可能处于左侧阶段的题材与个股，并通过结构、数据覆盖、控制组、信息增量和收益等多级 Gate，逐步判断一个研究机制是否值得继续。

早期系统以版本化 Python 脚本为主。每提出一个新研究假设，就复制上一版流程，再增加新的数据读取、指标计算和判断规则。这种方式在版本较少时开发效率较高，但随着实验数量增加，逐渐暴露出以下问题：

1. **研究逻辑重复。** 覆盖率、集中度、事件窗口、配对等计算被多个版本重复实现。
2. **流程与算法耦合。** 数据读取、指标计算、Gate 判断和结果写入混在同一脚本中。
3. **Agent 权限过大。** 如果让 Agent 直接控制数据源、参数和运行顺序，容易出现越权、跳步或口径漂移。
4. **证据链不完整。** 运行状态分散在 JSON、checkpoint 和日志中，中断后难以确认哪个结果才是权威状态。
5. **失败语义混乱。** 工程异常、数据不可用、样本不足和机制失败都可能被笼统记录为 `STOP`。
6. **历史结果可能泄漏。** 为验证新实现是否等价，流程可能提前读取旧结果，从而污染正式实验。

因此，项目需要解决的不只是“如何再写一个策略”，而是如何建设一套能够长期迭代、严格受控、完整留痕的专业研究平台。

## 二、需求分析与架构目标

结合业务特点，我将系统的核心质量属性确定为以下五项：

### 1. 可追溯性

每次研究必须明确绑定样本、数据快照、模块版本、工作流、阈值和 Agent 策略。任何结论都能追溯到对应输入与执行过程。

### 2. 可恢复性

流程可能运行数分钟甚至数小时。进程中断后应从最近一次有效状态恢复，不重复计算已经封存的节点，也不能重复累计逻辑数据访问次数。

### 3. 可维护性

量化公式、数据访问、研究规则和流程编排应解耦。修改一个模块时，不应影响无关工作流。

### 4. 可扩展性

后续新增量化模块或研究流程时，应通过标准契约完成注册和编排，而不是继续复制大型脚本。

### 5. 安全性与证据可信度

Agent 只能选择被允许的动作，不能修改冻结协议、跳过 Gate、提升数据权限或在正式终态前读取历史答案。

项目运行在单机、离线、单用户环境中，因此我没有引入微服务、消息队列和分布式调度，而是选择本地 SQLite、不可变文件和进程级隔离。这样既满足当前规模，又避免过度设计。

## 三、总体架构设计

系统综合采用分层架构、管道—过滤器和事件溯源思想，形成六层结构：

```text
┌─────────────────────────────────────────┐
│ 1. Agent 决策控制面                     │
│    选择下一项允许动作，不直接修改协议     │
├─────────────────────────────────────────┤
│ 2. 类型化 Research Workflow             │
│    编排节点、依赖、Gate、预算和信息上限   │
├─────────────────────────────────────────┤
│ 3. Research Kernel                      │
│    权限校验、状态机、首停、事务与恢复     │
├─────────────────────────────────────────┤
│ 4. Quant Module Library                 │
│    纯量化计算，可复用、无外部副作用       │
├─────────────────────────────────────────┤
│ 5. DataBroker / DataReader              │
│    固定快照、窄投影、统一数据访问         │
├─────────────────────────────────────────┤
│ 6. Evidence Journal + CAS               │
│    单一证据日志、内容寻址工件、回执重建   │
└─────────────────────────────────────────┘
```

各层只能通过明确契约交互，并遵循自上而下的控制依赖和自下而上的证据反馈。

## 四、各层关键设计

### 1. Agent 决策控制面

Agent 在系统中担任受约束的决策者。Kernel 每次只向 Agent 提供：

- 当前状态摘要；
- 允许执行的动作；
- 参数约束；
- 剩余预算；
- 当前允许的信息等级；
- 是否需要人工授权。

Agent 返回决策记录后，Kernel 再次校验状态是否过期、动作是否注册、参数是否越界。Agent 不能修改已冻结的样本、阈值、数据快照、模块版本和 Gate，也不能在正式停止后继续执行。

这种设计保留了 Agent 面对复杂研究流程时的判断能力，同时把最终控制权交给确定性的 Kernel。

### 2. 类型化研究工作流

Workflow 负责描述“模块如何组成研究过程”，但不包含具体量化公式。

每个节点需要明确声明：

- 输入和输出 Schema；
- 上游工件来源；
- 业务语义角色；
- 信息等级；
- 时间窗口；
- 可使用的数据能力；
- 是否为必经 Gate；
- 时间、内存和访问预算。

通过类型化边，系统可以在运行前发现输入输出不兼容、角色错配和时间范围漂移。例如，一个基于锚点前 60 日到后 40 日的数据工件，不能被下游重新解释为另一个时间窗口。

当前业务流程以线性研究链为主，因此 R3 只实现类型化线性 Workflow，没有直接建设动态 DAG、循环和通用 DSL。复杂度必须由真实业务需求推动，而不是提前预支。

### 3. Research Kernel

Research Kernel 是系统的执行核心，负责：

- 校验不可变 RunManifest；
- 接收和验证 Agent 决策；
- 生成稳定的 execution key 和 access key；
- 推进工作流状态机；
- 自动执行必经 Gate；
- 保证首个正式终态不可覆盖；
- 区分工程失败与研究停止；
- 支持中断恢复和确定性重放。

系统将状态拆分为四个正交维度：

```text
NodeExecution       = SUCCEEDED | FAILED
Availability        = READY | UNAVAILABLE
Gate                = PASS | STOP
ResearchDisposition = DATA_INSUFFICIENT
                      | ESTIMAND_INVALID
                      | MECHANISM_REJECTED
```

这样，Schema 错误只能形成工程 `FAILED`；数据不足可以形成节点成功后的研究 `STOP`；估计对象不成立和机制未被观察到也能被准确区分。

### 4. 量化模块库

量化模块库只保存可独立复用的确定性计算，例如：

- 加权覆盖率与集中度；
- 累计事件地标；
- MAD/Caliper 配对；
- 确定性无放回匹配；
- 事件窗口对齐和指标可用性。

模块只能接收不可变、类型化输入，不能直接连接数据库、访问网络、读取 Outcome 或写入 Journal。

每个模块通过模块标识、语义版本、输入输出 Schema、参数 Schema、数值契约和实现摘要进行固定。只有至少两个真实工作流使用完全相同的模块版本和契约，才能认定为稳定共享模块。

### 5. DataBroker 数据访问层

DataBroker 是研究数据的唯一入口，负责：

- 固定 generation 和数据快照；
- 批量读取，避免股票或日期级 N+1；
- 校验单位、有限值、业务键和数据血缘；
- 按信息等级输出最小必要投影；
- 拒绝网络回退、数据源切换和静默补值。

例如，在只需要判断数据是否可用的阶段，DataBroker 可以瞬时读取价格和成交量，但只向模块输出 READY、UNAVAILABLE、CONFLICT 等状态位图，不输出原始价格数值。这样可以在低信息等级阶段提前停止无效研究，减少计算和信息泄漏。

### 6. Evidence Journal 与内容寻址存储

系统使用 SQLite Evidence Journal 作为唯一权威状态，保存：

- 运行清单；
- Agent 决策；
- 节点执行；
- 数据访问；
- 追加式事件哈希链；
- 工件引用；
- Seal；
- 唯一正式终态。

大工件写入内容寻址存储。文件先在事务外完成规范编码和落盘，再由 Journal 事务提交引用。未被 Journal 引用的文件不属于正式证据。

数据读取前必须先提交唯一的 `AccessStarted`。如果进程随后崩溃，恢复时允许重新执行相同物理查询，但继续使用原 access key，因此逻辑访问仍只计算一次。

最终 Receipt 只是 Journal 的紧凑投影，不是第二权威。即使 Receipt 被删除，也能从 Journal 和内容寻址工件重建完全相同的结果。

## 五、R1、R2、R3 分阶段实施

为降低重构风险，我没有一次性替换旧系统，而是选择三个真实历史研究作为垂直切片。

### 1. R1：建立研究内核和单一证据链

R1 首先实现 Agent 控制面、Research Kernel、信息分级、Evidence Journal、CAS 和基础覆盖率模块。

系统使用固定数据快照，仅投影 SUPPORT 状态，在不读取旧核心数值的情况下，独立复现历史实验的数据覆盖不足结论。正式终态生成后，再读取旧工件进行兼容比较。

首版语义正确，但峰值内存超过 512 MiB。随后通过分批读取、并发只读和状态位图压缩，将峰值内存降到约 477 MiB，冷运行约 106 秒，warm audit 约 1.8 秒。

R1 证明了新架构具备可追溯、可恢复和低信息早停能力。

### 2. R2：验证量化模块跨工作流复用

R2 选择两个结构差异较大的历史研究：一个以周度单元和 21 日窗口为统计对象，另一个以题材边和 81/3 日篮子窗口为统计对象。

两条流程共用同一版本的加权可用性和集中度模块，不允许模块根据 workflow ID 编写隐藏分支。研究特有的角色、窗口和缺失语义由 Adapter 转换成公共输入。

两条正式路径均复现原有停止结论，冷运行约 242 秒，峰值内存约 490 MiB，warm audit 约 13 秒。R2 证明了模块库不是形式上的文件复用，而是基于相同实现、Schema 和语义契约的真实复用。

### 3. R3：完成静态目录和类型化编排

R2 仍存在模块执行器和 Codec 没有完全绑定、流程边缺少类型约束、Composition Root 过大的问题。

R3 因此增加：

- 静态 Module Catalog；
- 精确 Module Pin；
- Codec 和实现依赖闭包；
- Typed Linear Workflow Plan；
- Catalog-bound Runner；
- 显式数据视图投影节点；
- Workflow Builder Skill。

R3 将事件地标、确定性匹配和指标对齐等能力注册为候选公共模块，并用十节点线性工作流复现既有研究的首停语义。

至此，新增模块和新增工作流不再需要修改 Kernel，也不需要继续复制大型版本脚本。开发者或 Agent 可以通过统一 Skill 完成契约定义、模块脚手架、目录注册、流程编排和验收。

## 六、项目实施效果

经过三个阶段，平台在以下方面得到明显改善：

### 1. 可维护性提升

量化公式、数据访问、流程编排和证据封存实现解耦。研究版本不再直接复制底层公式，修改公共模块也能通过精确版本控制影响范围。

### 2. 扩展成本降低

新增研究流程主要变成“选择模块、编写 Adapter、声明类型化节点和 Gate”，不需要改动 Kernel 和 Journal。

### 3. 故障恢复更加可靠

运行进度由单一 Journal 决定，不再根据目录和多个 checkpoint 猜测。重复恢复不会增加逻辑访问次数，也不会覆盖首个终态。

### 4. 研究证据更加可信

正式流程在终态前无法读取历史答案；Oracle 只能在终态后做兼容比较，且不能修改正式结果。

### 5. 性能和存储可控

通过状态位图、流式计算、窄数据投影和内容寻址存储，系统避免重复保存大规模数值工件，并将运行时间、内存和工件大小纳入硬性 Gate。

需要特别说明的是：架构验收成功不等于研究机制有效。R 系列复现的是历史研究中的数据不足停止结论，它证明的是平台能够诚实、稳定地得到相同结论，而不是证明存在 Alpha。

## 七、设计难点与解决方案

### 1. Agent 灵活性与流程确定性的矛盾

解决方法是把 Agent 限定为动作选择者，由 Kernel 负责权限、状态和 Gate。这样既保留智能决策能力，又避免 Agent 自行修改实验规则。

### 2. 模块通用性与业务语义的矛盾

解决方法是采用“纯模块 + Workflow Adapter”。公共模块只处理稳定数学语义，题材角色、PIT 可见性和研究阈值留在 Adapter 与 Workflow 中。

### 3. 正式复现与历史答案泄漏的矛盾

解决方法是将正式路径和 Oracle 路径物理隔离。只有正式终态、性能证据和权限闭包封存后，兼容审计才能读取旧结果。

### 4. 完整证据与存储性能的矛盾

解决方法是 Journal 只记录状态、哈希和引用，大工件使用内容寻址存储；低信息阶段优先保存位图和摘要，不保存不必要的原始数值。

### 5. 架构扩展与过度设计的矛盾

项目坚持渐进式设计。当前工作流以线性流程为主，因此只实现类型化线性编排；等真实业务出现动态分支、循环或跨进程部署需求后，再评估 DAG 和服务化。

## 八、结论

本项目从真实的量化研究痛点出发，采用分层架构、管道—过滤器、状态机和事件溯源思想，构建了 Agent 驱动、Kernel 约束、模块与工作流解耦、证据链完整的研究平台。

R1 解决可信运行与故障恢复，R2 证明公共模块可以跨真实工作流复用，R3 完成静态模块目录与类型化编排。三轮演进遵循“先建立可信执行，再验证真实复用，最后提升编排能力”的顺序，有效避免了在需求尚未明确时过早建设复杂平台。

通过该项目，我体会到系统架构设计的核心不是堆叠技术，而是围绕业务目标和质量属性合理分配职责与权力。对于研究型系统，最重要的能力不是保证每次实验成功，而是确保每次成功或失败都真实、可解释、可复现，并能沉淀为下一次迭代的可靠基础。

| 记忆点 | 问题 | 方案 | 可展开的机制 | 效果 |
|---|---|---|---|---|
| Agent 控制 | 智能决策可能越权 | Agent 只选允许动作 | 状态摘要、动作白名单、参数校验 | 兼顾灵活性与安全性 |
| Workflow | 版本脚本复制、流程耦合 | 类型化流程编排 | Schema、角色、时间范围、Gate | 流程可读、可检查、可替换 |
| Kernel | 状态混乱、无法可靠恢复 | 统一执行内核 | 状态机、稳定执行键、首停 | 执行确定、失败可定位 |
| 量化模块 | 公式重复实现 | 建纯计算模块库 | 版本、接口契约、实现摘要 | 高内聚、可复用、易测试 |
| DataBroker | 数据口径和权限失控 | 统一数据访问边界 | 固定快照、批量读取、最小投影 | 数据一致、减少泄漏 |
| Evidence Journal | 多文件证据分散 | 单一事实源 | 事件哈希链、CAS、Seal、Receipt | 可追溯、可审计、可重建 |

三个实施阶段也按同一方式展开：

- **R1 为什么做**：先解决运行不可信；**做了什么**：Kernel、Journal、信息分级；**结果如何**：实现可恢复的低信息早停。
- **R2 为什么做**：验证模块不是“假复用”；**做了什么**：让同一模块服务两条真实流程；**结果如何**：两条流程均复现原结论。
- **R3 为什么做**：解决执行器、接口和流程边仍隐式的问题；**做了什么**：静态 Catalog、类型化 Workflow、Runner 和 Skill；**结果如何**：新增模块与流程不再修改内核。

遇到不同论文题目时，可以保持案例不变，只调整展开重点：

- 题目是**分层架构**：重点写六层职责、层间接口和依赖方向；
- 题目是**构件化/复用**：重点写量化模块、Adapter、版本契约和 R2 验证；
- 题目是**可靠性**：重点写状态机、幂等恢复、唯一终态和 Receipt 重建；
- 题目是**数据架构**：重点写 DataBroker、固定快照、数据血缘和最小投影；
- 题目是**智能体架构**：重点写 Agent 与 Kernel 的权力分离和最小权限；
- 题目是**架构演化**：重点写 R1、R2、R3 的渐进式实施和不过度设计。

> 我没有用复杂技术替代业务判断，而是通过分层、契约和证据链，把 Agent 的灵活决策约束在一个可复现、可恢复、可审计的量化研究平台中。
