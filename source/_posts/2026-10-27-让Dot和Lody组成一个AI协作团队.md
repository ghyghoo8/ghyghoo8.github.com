当一个任务需要查资料、改代码、跨机器执行，再把结果交回来验收时，问题很快就不只是“让哪个 AI 来做”。任务发给了谁？它在哪台机器上工作？另一位执行者看到的是不是同一份资料？回报里的“完成”，究竟代表会话结束，还是成果已经通过验收？

这篇文章记录我们围绕 **Dot、Codex Cloud 和 Lody** 建立的一套协作方法：由 Dot 对接目标和协调任务，开发任务在明确的执行环境中推进，需要跨节点协作时借助 Lody，最后沿原任务回传证据、复核成果。文中也会用一次真实的远端交接实践说明，为什么“任务结束”和“业务完成”必须分开看。

这是一套针对我们当前工作方式总结的实践，不是平台默认自动提供的组织架构。不同环节分别验证；文末会说明已经做到哪里，以及哪些链路仍需补证据。

## 先把三个工具和执行位置分清楚

[Dot](https://learn.chatgpt.com/docs/whats-new/september-28-october-2-2026#delegate-ongoing-work-to-your-dot) 是 ChatGPT 中可以持续处理任务的 Agent，可以使用自己的云电脑，也可以向 Work 或 Codex 委派任务。[Lody](https://lody.ai/zh/docs/) 则提供多 Agent 会话、远端机器和协作能力，适合在需要时连接已有执行节点。Codex Cloud 负责在选定的云环境中执行开发任务。

我们采用的分工可以画成下面这样：

![Dot 与 Lody 从目标、协调、执行到验收的协作流程](/imgs/dot-lody-collaboration.svg)

这是**我们选择的协作路线**，不是说每个任务都必须经过 Lody，也不是说只有 Dot 能创建 Codex 云任务。纯资料工作可以使用当次已有的资料工具；需要远端机器或已有 Lody 会话时，再进入跨节点流程。项目负责人可以由执行任务中的 Agent 承担，但“谁负责最终验收”需要在任务里说清楚，不能仅凭角色名称推定。

最容易混淆的，是以下几个位置：

| 对象 | 主要作用 | 需要单独确认的事 |
| --- | --- | --- |
| Dot 云电脑 | Dot 自己工作的环境 | 实际工具、网络、文件位置和权限 |
| Codex 云任务 | 在所选环境中处理具体任务 | 仓库版本、依赖、工具和任务引用 |
| Lody 工作区 | 组织机器、配置和会话的业务范围 | 当前身份、可见资源和操作权限 |
| 远端执行节点 | 实际运行 Agent 和生成产物的机器 | 节点在线、执行配置、身份和产物位置 |

一个会话链接可以帮助定位对象，但它不会自动带来完整聊天历史、对方机器上的文件或对外服务权限。同样，两台机器都出现 `/workspace`，也不意味着它们共享同一份文件。

## 让 Dot 通过 Codex 云环境使用 Lody

我们的做法是先准备好 Codex 云环境，再让 Dot 用它创建一项云任务。云任务根据需要通过 Lody CLI 联系已有执行节点，结果沿原任务回传给 Dot。

这条协作路线可参考前面的流程图。

准备时，在 Codex 云环境中配置仓库、依赖与网络，并通过环境变量提供 Lody CLI 所需的凭证。我们使用 `LODY_CLI_TOKEN` 这个变量名，它是本项目的约定：**变量存在不等于 CLI 已登录**。任务需要在已有授权范围内复用有效身份或显式完成认证；凭证不要放进聊天、仓库或共享快照。

Codex 的直接环境变量会传给程序；网络密钥则由代理向允许的 HTTPS 目标替换占位符。若 CLI 需要直接读取真实凭证，不能未经验证把网络密钥占位符当作有效登录材料。具体配置见 [Codex 云环境文档](https://learn.chatgpt.com/docs/environments/cloud-environments#configure-environment-variables-and-network-secrets)。

云任务准备好 CLI 和身份后，按实际授权选择 Lody 工作区、机器和 Agent 配置；执行节点还要具备运行进程及模型凭证。首次接入可参考 [Lody 快速开始](https://lody.ai/zh/docs/quickstart/) 和 [CLI 文档](https://lody.ai/zh/docs/cli/)，具体操作以当次版本帮助为准。派发后保留原生会话和回合引用，核对任务结果与产物，再交由 Dot 汇总和负责人验收。

这里的 CLI 运行在 **Codex 云任务**中，不能因此推断 Dot 自己的云电脑也已完成安装或登录。我们已验证过云控制端经 Lody 协作远端并回传产物；这项验证与 Dot 协调云任务的记录属于不同片段，并不证明完整链路已经自动闭环。


## 一次任务怎样从目标走到验收

### 1. 把目标写成可验证的任务

先说清楚“希望得到什么”，再约定“如何判断完成”。例如，请执行者修改一项功能，不能只写“优化一下”；至少应说明预期行为、相关仓库或资料、允许修改的范围，以及需要运行的检查。

对一项开发任务，我们通常会确定：

- **目标和成功标准**：要交付什么，哪些行为或检查需要通过。
- **责任与授权**：谁负责决策和验收，谁协调，谁写入产物；已有授权内的步骤不反复确认。
- **输入与范围**：仓库、基准提交、已有资料版本、可修改路径和不涉及的内容。
- **依赖与交付**：执行位置、前置条件、产物在哪里，以及需要回传哪些证据。

一个人可以承担多个角色。关键是责任明确：同一项产物在同一时间只有一个当前写者；同一项任务有明确的派发和后续协调者。并行之前，先确认任务是否真的独立，避免两个会话同时改同一处文件。

### 2. 先准备执行环境，再派发一次

Dot 接到任务后，在我们的项目分工中负责发起独立 Codex 云任务；执行端先核对当前环境、源码和必要工具，再决定是否需要通过 Lody 联系已有节点。

进入 Lody 流程时，先确认目标工作区、机器和执行配置，准备对方实际能取得的输入，然后发起请求并保存返回的原生会话与回合引用。**在线只是一个状态，不能证明目标 Agent 的模型身份、文件访问和任务执行能力都已经就绪。**

如果输入是一份附件或文件，还要确认它属于哪台执行器、通过什么渠道交付，以及接收方实际取得了什么。传递一个路径字符串并不等于文件已经传过去。

### 3. 回报结果时，把证据和结论放在一起

执行者回传的内容应让接手的人能回答：

1. 这是哪一次任务、哪个回合的结果？
2. 哪些步骤真的执行过，结果是什么？
3. 产物在哪里，能否由验收者取得和检查？
4. 哪些部分未验证，是否存在阻塞或待决定事项？

例如，测试通过的日志证明这次测试的结果；它不自动证明生产部署已经完成。文件存在也不自动证明技能已经被 Agent 读取。工具返回“请求已接收”，更不等于远端任务已经完成。

### 4. 负责人复核，Dot 汇总

执行者先自检并提供对应版本的产物和证据；需要独立复核时，由适合的复核者检查。项目负责人再依据约定的验收标准给出结论，Dot 面向提出目标的人汇总结果、未决事项和下一步。

Dot 创建任务或转交报告，并不会因此自动成为所有业务的最终验收者。对于小任务，这些责任可以在一个回合内完成；对于复杂任务，则应保留清楚的负责人、复核范围和证据来源。

## 一个真实片段：远端回合结束了，为什么还不能算完成？

在一次跨端验收中，我们用 Linux 云控制端通过 Lody 联系已有的远端 Agent，目标是让远端读取所需资料、生成一个确定性的结果，再把结果交回来核对。

第一次回合的原生状态显示 `completed`，但实际回报是 `DOWNLOAD_FAILED`：所需源码没有取得，也没有产生结果。于是这次业务验收不能通过。**会话回合结束，只说明这一回合结束；它没有替代对目标产物的检查。**

确认问题范围后，我们没有重复创建一份新任务，而是在**原会话**中发起明确的新回合，通过附件提供执行所需资料。远端 Agent 报告解包、读取技能及参考材料，并生成了确定性 JSON。随后又在原会话发起只读复核回合，让远端回传产物字节、摘要，以及根据临时 challenge 计算的校验值；控制端核对回合关联和回传内容。

这段实践给我们三个教训：

- **先看实际产物和错误，再看状态标签。** 第一次 `completed` 没有掩盖下载失败。
- **恢复时沿原关联继续。** 明确发起新回合，保留失败和后续处理的关系，而不是把超时或失败直接当成重建理由。
- **说清证据来自哪里。** 这次字节由远端 Agent 回传后再核对；它不证明控制端直接访问了远端文件系统，也不证明平台自动发现并加载了技能。

这次验证覆盖了云控制端通过 Lody 协作远端、显式读取资料和产物回传的子范围。它**不是**一次已经证明由 Dot 全程发起并闭环的端到端测试。

另一份由用户转交的接入回执记录了 Dot 读取组织协议、协调云端任务，以及远端执行和复核角色读取相应指引的过程。它补充的是组织协作接入证据；与上面的远端产物交接不是同一趟测试，不能拼成一次完整闭环。实际角色绑定、自动发现和业务验收仍需分别核实。

## 遇到不确定，先对账

跨会话协作最危险的时刻，往往不是收到明确失败，而是请求发出后没有得到明确结果。例如创建任务超时，可能是请求没有被受理，也可能是任务已经创建而回执丢失。

我们采用的处理方式是：

| 情况 | 做法 |
| --- | --- |
| 派发后超时 | 先按已有原生引用查询任务与回合；无法唯一确认时保留 `UNKNOWN`，不自动重复派发 |
| 部分步骤成功 | 保留已经成功的结果，逐项核对未确认部分，不把整批当作失败重放 |
| 执行端离线或缺身份 | 报告具体缺口，不擅自换机器、换账号或扩大访问范围 |
| 只看到旧回合或状态摘要 | 核对目标会话、对应回合、结果来源及新鲜度，再判断是否需要继续观察 |
| 产物回传受限 | 说明产物所属位置和可用交付通道；没有取得内容时保留证据缺口 |

这些规则并不提供平台级的分布式锁或“恰好执行一次”保证。它们的作用是让参与者在证据不足时停止猜测，避免把一次不确定的操作变成多次不可控操作。

## 可以直接复用的交接卡

不是每个小任务都需要填长表。跨端、并行或需要他人接手时，可以按下面的格式交接，只保留实际需要的项目：

```text
目标与成功标准：
已授权范围与限制：
负责人、协调者、产物写者：
输入资料及版本 / 基准提交：
执行位置、目标节点和工作范围：
Codex 任务引用：
Lody 会话及回合引用（如使用）：
产物位置、取得方式与验证证据：
已完成、失败或 UNKNOWN 的事项：
下一步、责任人和解除阻塞所需条件：
```

交接卡不存凭证，也不把不同系统的任务 ID 混填。公开分享时，还应删除真实机器标识、私有路径、业务数据和其他不适合公开的细节。

## 从最小闭环开始

如果想尝试这套方法，可以先选一个没有外部写入的小任务，例如让远端 Agent 根据给定输入生成一个小文件。给出明确目标和成功标准，记录实际任务引用，再由接收方读取并核对结果。只有这个过程跑通，才逐步加入并行任务、代码集成或业务系统操作。

每增加一个环节，都分别验证：**文件是否到达、指引是否实际读取、工具是否可调用、任务是否执行、产物是否可复核、负责人是否验收。**这些证据可以互相支撑，但不能互相替代。

工具让协作成为可能，清晰的责任、交接和验收让协作可以持续。Dot 帮我们保持目标和协调，Lody 帮我们连接需要协作的执行节点，而每个任务最终仍要回到一个问题：我们能否根据真实证据，解释这次工作完成到了哪里？
